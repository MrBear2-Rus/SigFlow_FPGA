# TraceBridge 升级与拓展候选清单

> 日期：2026-10-09  
> 架构取向：板端“小而美”，板外“大而美”；本版已据此重新划分职责、优先级与实施路线。  
> 范围：SigFlow TraceBridge 的板上采集、调试构建、波形分析、仿真重放及平台化能力。  
> 性质：供产品与技术选型使用的候选方案，共 36 项；不表示全部立项，也不表示下文功能均为现有缺失项。  
> 调研方式：阅读当前仓库的设计、验收、RTL 说明和关键实现，并查阅 AMD 官方调试文档。本次未重新编译、运行回归或连接板卡。

## 1. 建议定位

建议将 TraceBridge 升级为“轻量板端采集核 + 强大板外调试平台”。FPGA 中的 ILA、触发、协议和控制模块围绕小体积、低资源、低扰动做精细升级；PC/工作站、实验室代理和可选服务端承担复杂分析、仿真重放、自动化和协作，允许做成完整的平台。

对标 Vivado 时，优先对标用户完成调试任务的能力与体验，按上述分工实现。协议解码、复杂规则、事务差分、根因分析等优先放在板外；确实要求在故障发生当拍执行的功能，才考虑增加受限且可裁剪的板端模块。

优先价值有三条：

1. **板端精简可靠**：做好有限窗口采样、基础触发、低成本传输和必要状态，配置与实际能力一致。
2. **板外分析强大**：从逐位看波形升级为事务、规则、性能、重放和证据分析，构建源码与硬件的完整调试工作台。
3. **系统迭代高效**：通过自动选探针、缓存、任务 API、回归和协作提高效率，新增软件功能尽量复用同一位流。

### 1.1 板端与板外的职责边界

| 位置 | 应承担的职责 | 扩展策略 |
| --- | --- | --- |
| FPGA 默认采集核 | 本域有限窗口采样、现有基础触发、环形 RAM、冻结与读取、必要状态和明确的链路完整性语义 | 保持小型、参数化、可综合；优先复用现有比较器、计数器和存储 |
| FPGA 按需扩展 | 少量额外采样域、小型触发条件、有限计数器、少量 VIO 控制位、必要的时间标记 | 每项单独预算，构建时裁剪；未选用时不实例化 |
| PC / 工作站 | 波形工作台、协议解码、离线断言、事务差分、重放、故障最小化、证据图、智能探针规划、构建缓存 | 主力研发方向，允许丰富 UI、索引、算法和数据模型 |
| 板外代理 / 服务端 | 设备访问、任务调度、板卡池、远程协作、长期归档和计算任务 | 按需部署；复杂度不转移进 FPGA，也不要求基础调试必须联网 |
| 专用硬件研究 | DDR 高速流式采集、通用复杂触发机、大型总线主机、SerDes 测试 | 从默认路线移出；仅在明确需求与实测预算支持时单独立项 |

这里的“板外”按执行位置划分：FPGA 内的软核处理器、片上固件和它们占用的 RAM 仍计入板端成本；运行在独立 PC 或独立设备上的代理才属于板外。

### 1.2 “小而美”的准入规则

- **默认零附加实例**：纯软件升级复用现有采集位流；可选 RTL 必须在构建时真正消除，不能仅用运行时开关关闭。
- **围绕当前基线优化**：默认保留 32×1024 作为比较基准，不为界面丰富自动扩宽、加深或增加时钟域。预算按同 DUT、同器件、同约束的实测增量制定，不虚构统一百分比承诺。
- **按必须实时的程度下沉**：优先在宿主解释和编排；无法用已采数据满足、且确需板端实时捕获的条件，才下沉为小型比较器、计数器或有限状态逻辑。
- **少量且明确的硬件原语**：一个小型端点服务多种软件分析，避免每种协议、每个规则各实例化一套大型硬件核。
- **节省资源不省略语义**：明确 minimal/full 的完整性与身份保证；丢样、时间空洞和未知身份必须可见，不能为了小体积静默丢失正确性信息。

### 1.3 “大而美”的重点投入

允许并鼓励在板外建设：大规模波形索引与可视化、多协议插件、规则引擎、事务数据库、批量会话比较、仿真重放与场景最小化、证据化诊断、智能探针选择、跨项目回归、设备管理和多人协作。每项能力仍应有清晰模块边界和可验证结果。

板外算法只能解释已捕获的信息。不能用软件压缩延长既有板上 RAM 的物理采集窗口，不能离线恢复未捕获的边沿，也不能用宿主循环布防代替无盲区硬件采集。

“创新”在本文中指适合 TraceBridge 的差异化产品方向，不代表已证明其他工具均不具备，也不代表专利新颖性结论。

## 2. 当前基础与必须保留的边界

### 2.1 已核实的项目基础

| 能力 | 当前资料与代码体现 | 对升级规划的意义 |
| --- | --- | --- |
| 调试契约、会话和构建指纹 | `DebugContract`、`DebugSession`、`DebugFingerprint` 与相关 schema 已存在 | 应扩展现有模型，避免另起一套配置体系 |
| 非侵入影子构建 | `DebugOverlayBuilder` 已生成调试 wrapper 和约束，另有 Overlay 修复记录 | 自动插桩属于已有能力深化，重点是层级、语言覆盖和构建效率 |
| 参数化片上采集 | `sf_micro_ila` 默认 32 bit × 1024 样本，使用 BSRAM | 扩宽、加深、分段、压缩都要考虑小器件资源 |
| 增强触发 | RTL 说明已有掩码、匹配计数、停滞、握手超时、上升/下降沿及抽取 | 优先通过宿主规则编排复用已有原语；复杂序列先离线分析，必要时才增加有限触发逻辑 |
| 两种协议档位 | `minimal` 默认低资源；`full` 提供 COBS/CRC、PING、GET_INFO、在线指纹和扩展配置 | 同名 GUI 配置不应掩盖档位差异；能力协商是优先基础项 |
| 双端口 RAM 并发读写 | 文档说明采集中可并发读回 | 并发读写不等于全速、无限时长、无丢样流式采集 |
| 多时钟原语 | `sf_cdc_control`、`sf_multiclock_capture` 已存在 | 多时钟不应从零重做，应接通 Overlay、协议、宿主和时间轴 |
| 多时钟产品闭环限制 | `DebugOverlayBuilder.cpp` 明确阻断多时钟 Overlay；修复草案注明分域回读待实现 | 这是明确扩展项，按需接通少量域；不作为单域软件升级的前置条件 |
| 重放、差分和定位 | `ReplayScenario`、`WaveformAligner`、`WaveformComparator`、`RootCauseGraph`、映射生成器已存在；P4 验收文档覆盖相关流程 | 应强化可重复性、语义、证据和规模，而非仅新增入口按钮 |
| 传输抽象与脚本基础 | `ITransport`、串口/管道/FTDI 实现文件及多种 smoke 脚本已存在 | 新传输、无界面运行和持续集成可复用已有基础，但文件存在不等于所有后端均已完成板测 |

### 2.2 当前协议差异应在产品中明确呈现

| 维度 | minimal | full |
| --- | --- | --- |
| 主要目的 | 专用 UART、低资源调试 | 完整性校验和更丰富配置 |
| 触发 | 单次掩码比较 | 扩展触发参数，包含计数、停滞、握手和边沿模式 |
| 抽取 | 当前限制为 `decimation=1` | 已有抽取配置链路 |
| 链路校验 | 固定帧，无 COBS/CRC | COBS + CRC |
| 板端身份查询 | 无 PING、GET_INFO、在线指纹回读 | 支持相关能力 |
| 指纹意义 | 宿主会话产物标识 | 可结合板端信息校验 |

以上来自当前 `rtl/debug/README.md`，不应将 full 的保证套用到 minimal。后续可以升级协议，但必须保持旧位流的行为可识别。

### 2.3 历史资源数据的使用方式

仓库说明记录过以下 Tang Nano 9K 实现结果：最小调试示例约 579 LUT4、319 DFF、2 BSRAM，Fmax 112.41 MHz；完整协议 Overlay 约 1496 LUT4、526 DFF、2 BSRAM，Fmax 62.64 MHz。它们属于特定版本、配置和示例的历史数据，本次未复测，不能作为任意用户设计的性能承诺。

这些记录说明：协议和控制逻辑也是显著成本来源，升级时应同时比较资源、时序、传输效率和可靠性。

## 4. 候选项总览

优先级：**P0** 为轻量默认链路的可信基础；**P1** 为板外主力能力与低成本高收益升级；**P2** 为按需板端增强或平台扩展；**P3** 为较重硬件与工具链研究项。混合项分别标明板外与板端的优先级，软件路线不等待可选硬件完成。

工作量：**S** 为局部宿主/文档/适配改动；**M** 为多个软件模块或一个较小 RTL 模块；**L** 为 RTL、协议、宿主、GUI 的闭环；**XL** 为涉及新硬件、复杂工具链或多端部署。这里是相对规模判断，不是工期报价。

板端成本中的“无新增”以复用已有探针与采集数据为前提，新增观测信号本身仍可能增加探针宽度和布线负担。

## 5. 采集与触发升级

### TB-01：能力协商、协议版本与配置一致性

- **要解决的问题**：契约字段、GUI 可选项和位流实际支持能力可能不同，尤其 minimal/full 差异容易造成误解。
- **升级内容**：建立 `capabilities` 描述，覆盖协议版本、域数、探针宽度、深度、触发类型、时间戳、压缩、在线控制等；新协议可查询，旧协议由明确的兼容档案描述。GUI 按能力禁用不支持选项并说明原因。
- **实现前提**：定义兼容矩阵、能力 schema 和配置校验入口；区分宿主指纹、板端可核验指纹和未知身份。运行时配置应有独立哈希，不必把每次触发阈值修改视为新设计。
- **验收标准**：minimal 请求握手超时时在布防前拒绝；旧位流不因缺失新字段而被误识别为新版本；不匹配信息可追溯到具体字段。
- **价值与取舍**：这是其他高级功能的基础；可先只做宿主一致性和兼容档案，再升级板端发现能力。

### TB-02：多时钟域采集与分域回读闭环

- **要解决的问题**：现有多时钟原语尚未形成统一产品链路，不能据此宣称已能完整调试多时钟工程。
- **升级内容**：仅为用户选中的域生成独立采样核，首版限定少量域并共享受控回读通道；Overlay 连接 CDC 控制；协议携带域 ID、域内样本序号和状态；多域配置、时间轴解释和展示放在宿主。
- **实现前提**：先完成“两域独立采集”；再加入跨域触发和同步锚点。跨域触发存在同步延迟，公共时间关联必须说明误差，不能默认不同域的同一序号代表同时发生。
- **验收标准**：两个非整数频率比时钟域均能生成、下载、触发、回读；一个域停钟时另一域仍可查询；不存在多位信号直接跨域拼接采样。
- **价值与取舍**：覆盖 FIFO、桥接、异步接口等场景；每域采样 RAM 与逻辑资源独立预算。多域为按需增强，不自动复制所有时钟域；单域采集不承担未启用域的资源。

### TB-03：调试时钟与复位恢复机制

- **要解决的问题**：用户时钟停摆、复位异常或门控时钟关闭时，调试链路也可能无法响应。
- **升级内容**：在板卡允许时，将调试控制/传输域与用户采样域分离；增加时钟心跳、复位原因、域超时、重新布防和采集取消机制；区分调试复位和 DUT 复位。
- **实现前提**：稳定参考时钟、跨域请求/应答和复位释放同步；没有独立参考时钟的目标板需明确降级能力。
- **验收标准**：DUT 停钟后仍能读取“采样域未推进”状态并取消任务；恢复时钟后无需重启 IDE；不以固定常高复位替代需要复位的控制状态初始化设计。
- **价值与取舍**：按目标选用最小必要心跳、复位同步和超时逻辑，复杂诊断在宿主完成；不为所有单域设计强制增加完整独立时钟基础设施。多域恢复逻辑需要负向测试。

### TB-04：宽度、深度与资源预算配置器

- **要解决的问题**：固定 32×1024 难以同时满足宽总线、较长故障窗口和小器件资源限制。
- **升级内容**：宿主提供宽度、深度、抽取和探针裁剪方案，按目标器件计算 RAM 打包与逻辑估计，展示采样时间和回读成本。默认保留 32×1024；16/64/128 bit 等是按需构建候选，不要求默认核全部兼容运行时切换。
- **实现前提**：核对当前 wrapper、协议、解码器和 schema 中的 32-bit 假设，不能只修改 RTL 参数。预算估计与实现实测应分别展示。
- **验收标准**：先验证默认 32×1024 不回退；对选入支持矩阵的配置，例如 16×2048 或 64×512，分别验证打包、位序和端到端采集；资源不足时优先建议裁探针和分次实验。
- **价值与取舍**：显著扩大使用范围；宽度×深度只给出原始存储量，不能替代实际 BSRAM 映射结果。

### TB-05：触发规则编排与序列分析

- **要解决的问题**：现有单类触发不足以捕获“A 发生后，B 在规定时间内未出现”等过程性错误。
- **升级内容**：宿主提供丰富 DSL、图形化序列和模板，将能执行的条件映射到已有掩码、边沿、计数及超时原语；其余序列在捕获窗口中离线匹配。确需当拍布防/冻结的场景，可选择生成只满足该任务的小型状态逻辑。
- **实现前提**：配置中明确区分板端实时触发、宿主采集编排和离线分析条件；离线序列不保证目标事件已进入窗口，宿主命令到达也不具备 FPGA 周期精度。明确墙钟周期与合格采样周期。
- **验收标准**：现有硬件支持的规则不新增 RTL；离线匹配能定位窗口内已知序列；需板端执行但不支持的条件明确拒绝或生成预算可见的选装核，不能静默降级。
- **对标与取舍**：参考 Vivado 的 [基础触发与 Trigger State Machine](https://docs.amd.com/r/en-US/ug835-vivado-tcl-commands/run_hw_ila) 使用场景，默认不引入通用板端触发虚拟机或大型多比较器阵列。

### TB-06：重复采集与稀有事件管理

- **要解决的问题**：一次触发只保留一个窗口，难以观察间歇性错误的分布与共同特征。
- **升级内容**：首选宿主自动布防、回读、归档和再布防，提供窗口列表、事件分类、聚类及停止条件；无盲区或紧邻事件确有需求时，再选装有限硬件分段缓存。
- **实现前提**：宿主重复采集保留回读/重新布防盲区记录，不宣称与硬件多窗口等价。硬件分段只允许固定且有界的窗口数，优先复用同一 RAM。
- **验收标准**：周期性错误可归档为多个独立会话并进行聚类；各窗口触发位置、死区和采集 ID 可追溯；硬件选装未开启时不增加窗口管理 RTL。
- **对标与价值**：Vivado ILA 有多窗口和触发位置控制，见 [采集窗口属性](https://docs.amd.com/r/en-US/ug835-vivado-tcl-commands/run_hw_ila)；适合偶发握手、复位和状态机错误。

### TB-07：条件采样、时间语义与分层压缩

- **要解决的问题**：大量空闲周期占满 RAM；跳过周期后若仍画成等间隔波形，会造成时间解释错误。
- **升级内容**：板外负责会话压缩、索引和格式转换；板端优先复用已有抽取/门控，仅在需要非均匀条件采样时选装简单谓词与有界时间差记录。RLE 等板端压缩单独验证收益后再考虑。
- **实现前提**：固定抽取可由已知周期与倍率重建时间轴，非均匀采样须有实际时间标记；宿主压缩只减少存储/传输后的数据体积，不延长既有板上窗口。板端压缩不得以平均压缩率承诺最坏无丢样。
- **验收标准**：默认数据路径资源不增加；板外压缩解码保持值和时间；条件采样的间隔与时间差溢出均正确，时间空洞可见。
- **价值与取舍**：优先提高板外存储与分析效率；板端先做少量门控和时间语义，避免为压缩算法堆积宽计数器和复杂编码器。

### TB-08：智能探针规划与分组采集

- **要解决的问题**：更换少量观测信号就重跑完整构建，影响迭代速度。
- **升级内容**：宿主依据依赖图、异常候选和预算推荐最小探针集，按状态机/FIFO/接口分组，并规划可复现实验的分次采集；对频繁切换场景，才预埋小规模候选组和受限复用器。
- **实现前提**：不同次采集不默认具有同一故障现场；需要可重复激励或清晰的对齐锚点。运行时只能选择已布线信号，不预埋整设计的大型多路选择网络。
- **验收标准**：规划器解释每条探针的作用和成本；分次实验明确标识采集 ID；选装复用器的位序正确且资源可量化；关闭选装时不保留复用树。
- **价值与取舍**：用板外智能减少板端观察宽度；少量额外 LUT 换取切换效率时，必须证明比重新构建更有价值。

## 6. 传输、存储与会话升级

### TB-09：UART 批量回读与断点恢复

- **要解决的问题**：当前完整协议 RTL 为降低资源采用单样本 READ，应答和往返开销可能成为回读瓶颈。
- **升级内容**：新增固定且有界的小批量读取，块大小经实测选择；板端流式发出数据，不复制整块缓存；块校验与必要状态维持明确语义，重试、进度和恢复调度主要在宿主。
- **实现前提**：保持流式响应编码，避免恢复大规模可变长数组选择树；冻结数据的恢复必须校验采集 ID 和指纹，不能把新旧采集混合。
- **验收标准**：比较升级前后的有效 payload 吞吐、总耗时和 LUT；注入错误仅重传受影响块；断开重连不产生伪完整 VCD。
- **价值与取舍**：通常比直接引入全新高速接口更容易落地，优先对 full 做可靠批量读回。

### TB-10：多传输后端与链路自诊断

- **要解决的问题**：不同板卡的 UART、USB、FTDI 和驱动环境差异较大。
- **升级内容**：复用 `ITransport`，按需求补齐 USB FIFO、TCP 桥接或厂商公开 JTAG 通道；统一设备枚举、超时、取消、链路统计、吞吐测试和兼容性报告。
- **实现前提**：区分字节传输层和调试协议层；已有 FTDI 文件先评估可用性和实测状态，不直接宣称完成。JTAG 后端依赖公开接口、驱动及板级连接。
- **验收标准**：同一冻结采集通过两个后端回读得到一致结果；驱动缺失、设备占用和传输中断均能给出准确错误。
- **价值与取舍**：按目标用户板卡选择后端，避免同时维护多个缺少测试硬件的实现。

### TB-11：高吞吐流式采集与外部存储

- **要解决的问题**：片上 RAM 只覆盖短窗口，串口无法长期搬运高速并行采样。
- **升级内容**：提供有界持续采集、双缓冲/DMA、带宽监测和丢样标记；在具备条件的板卡上增加 DDR 缓存、USB 高速接口或以太网输出。
- **实现前提**：明确板卡存储与接口资源，定义采样与传输速率预算。例如 128 bit × 100 MHz 的原始数据为 12.8 Gbit/s，尚未包含封装开销；低速链路只能依靠过滤、压缩或短时缓冲满足需求。
- **验收标准**：公布指定配置下持续时间、实际吞吐和丢样率；超载时明确报缺口。观察 DUT 时不能未经设计就用背压暂停 DUT 来伪造无丢样。
- **价值与取舍**：适合高吞吐原型，但应作为新硬件档位，不强行加入 Tang Nano 9K 默认核。

### TB-12：故障会话包与离线分析

- **要解决的问题**：转交一份 VCD 通常缺少探针映射、位流身份、触发配置和构建背景。
- **升级内容**：统一归档 manifest、契约、运行时配置、原始采集、时间语义、映射、比较结果和必要日志；支持导入、校验、只读分析及版本迁移。
- **实现前提**：复用现有会话/schema，规定必需与可选产物；源码可选打包，包内使用相对路径，避免依赖开发机绝对路径。
- **验收标准**：另一台无板卡机器能打开会话并复现相同差分结果；缺文件、损坏和不支持的 schema 均明确提示；默认不夹带无关工程文件。
- **价值与取舍**：适合团队协作、教学提交和问题归档，主要为宿主侧工作。

## 7. 波形、协议与性能分析升级

### TB-13：波形分析工作台

- **要解决的问题**：采到数据后仍需频繁手工寻找边沿、计算周期和整理信号。
- **升级内容**：信号分组、固定行、总线拆合、枚举状态名、数值/定点显示、光标测量、事件书签、搜索、差异区导航和布局保存；进一步支持大波形索引、多会话联查、事务与源码联动、后台分析及可停靠工作区，均在板外完成。
- **实现前提**：复用 WavePanel，定义统一的采集数据接口；显示降采样与实际采集抽取需分别标识，缩略视图不能吞掉短脉冲。
- **验收标准**：用已知脉宽/周期样例核对测量；重开会话恢复布局；较大波形仍可交互，并公布测试文件规模和响应时间。
- **价值与取舍**：覆盖面广，建议先做搜索、枚举、测量和布局，再投入超大波形引擎。

### TB-14：总线与协议事务解码

- **要解决的问题**：用户需逐根观察 valid/ready/data，难以快速判断“一次事务发生了什么”。
- **升级内容**：首批支持 UART、SPI、I²C、valid-ready；随后扩展 AXI-Lite、AXI4、AXI-Stream、Wishbone 或 APB。显示帧、地址、方向、数据、响应、延迟及对应波形区间。
- **实现前提**：协议配置包括位序、极性、采样域和接口类型；区分内部同步总线与外部引脚采样，缺失关键边沿时给出“不足以解码”。
- **验收标准**：以已知事务样例核对帧与字段；覆盖截断帧、错误响应和背压；点击事务能跳到原始波形。
- **对标与价值**：借鉴 [System ILA 接口级调试](https://www.amd.com/en/products/adaptive-socs-and-fpgas/intellectual-property/system-ila.html)，优先做宿主离线解码以减少板端资源。

### TB-15：离线规则检查与轻量违例触发

- **要解决的问题**：仅展示波形，用户仍需自行判断协议违规和状态约束破坏。
- **升级内容**：主力建设板外规则引擎、协议规则库、事件查询与批量报告，覆盖 valid 等待时数据稳定、FIFO 非法读写、状态机非法状态和响应超时。需要实时冻结窗口时，只选装少量简单违例谓词，并复用现有触发路径。
- **实现前提**：定义可支持的受限断言子集、复位屏蔽和时钟语义。超时可以是项目规则，不能把自定义阈值说成所有协议都要求的违规；不承诺任意 SVA 可综合。
- **验收标准**：同一采集增加规则不需要重烧录；窗口内注入违例可定位准确周期；缺信号和窗口边界给出不可判定；选装监测器与离线检测在支持范围内一致，并记录每条硬件规则的增量资源。
- **对标依据**：AMD 的 [AXI Protocol Checker 与 ILA 集成](https://docs.amd.com/r/en-US/pg101-axi-protocol-checker/Integration-into-Vivado-Logic-Analyzer-and-Vivado-Debug-Nets) 提供相关场景参考。

### TB-16：性能分析与事件统计

- **要解决的问题**：短窗口波形难以回答长期吞吐、背压和尾延迟问题。
- **升级内容**：板外从波形/事务计算窗口内吞吐、停顿占比、延迟分布、水位变化及多版本趋势。确需连续长期统计时，板端仅选装少量计数器/极值寄存器，直方图与报告优先在宿主生成。
- **实现前提**：采集窗口统计不能宣称代表全部运行时间；抽取可能漏掉握手事件，不能直接据此报告精确全局吞吐。复杂 outstanding 事务匹配优先板外执行，长期计数明确范围与溢出。
- **验收标准**：已知窗口下结果与参考一致；图表注明观测时段、覆盖和估计属性；可选计数器快照、清零与溢出行为有定义。
- **价值与取舍**：板外可以建设完整性能仪表盘，默认不引入板端事务跟踪表或大型直方图存储。

## 8. 在线控制与激励升级

### TB-17：丰富 VIO 面板与少量控制端点

- **要解决的问题**：板上验证常需要改阈值、切模式、发启动脉冲或控制 DUT 复位。
- **升级内容**：宿主提供丰富状态面板、位域、滑块、枚举、预置、脚本和操作日志；板端仅保留用户显式选择的少量控制位、参数寄存器和脉冲端点，按需提供原子提交及生效确认。
- **实现前提**：仅控制预先插入的调试端点，采用显式 mux/寄存器接口，不能在运行时任意强驱动内部网。跨域写入使用握手，断连后的值由目标配置规定。
- **验收标准**：多位参数不会半更新；脉冲在目标域恰好持续规定周期；控制动作及生效确认进入会话记录。
- **对标依据**：Vivado [VIO 可以监视并驱动内部信号](https://docs.amd.com/r/en-US/2026.1/ug912-vivado-properties/HW_VIO)。

### TB-18：寄存器与存储器语义浏览器

- **要解决的问题**：裸地址读写不易理解，也容易误触发有副作用寄存器。
- **升级内容**：导入或维护寄存器描述，展示名称、地址、位域、枚举、访问属性和复位值；支持快照、前后差分、有限轮询以及 RAM 区间查看。
- **实现前提**：需要 DUT 提供可访问的调试总线/CSR 桥。读取清零、写一清零、FIFO 弹出等副作用必须进入模型，默认只自动轮询无副作用字段。
- **验收标准**：大小端、访问宽度、地址对齐和位域写入正确；有副作用访问需显式操作；读失败不显示为合法零值。
- **价值与取舍**：适合软核 CPU、控制器和 SoC 项目，可与 TB-19 共用访问服务。

### TB-19：总线事务编排与可选访问桥

- **要解决的问题**：调试内存或总线从设备往往需要额外测试固件或 testbench。
- **升级内容**：宿主承担事务脚本、轮询、模板、数据校验和日志；优先利用 DUT 已有 UART 命令、CSR、处理器或访问桥。缺少通道时仅按需选装简单访问桥，复杂 AXI 主机移入专项研究。
- **实现前提**：利用已有处理器时须说明所需固件及对 DUT 的影响；FPGA 内新增软核仍算板端成本。新增桥必须有超时、地址范围和错误响应，不为通用脚本功能实例化大型执行引擎。
- **验收标准**：正确处理目标无响应、非法地址、背压和总线错误；取消任务后主机状态可恢复；事务日志与采集波形对应。
- **对标依据**：参考 [UG908 的 JTAG-to-AXI 系统通信工作流](https://docs.amd.com/r/en-US/ug908-vivado-programming-debugging)，实现方式可适配 TraceBridge 的公开工具链。

### TB-20：可重复激励与受控故障注入

- **要解决的问题**：许多错误无法稳定复现，需要可控地制造延迟、背压和异常输入。
- **升级内容**：优先在板外仿真/重放中提供随机种子、背压、复位、超时和位翻转模型，建设实验编排器与结果分析。实板需要时只插入少量、明确位置的故障节点，复杂场景由宿主组织。
- **实现前提**：周期精确的实板动作仍需有限的本地逻辑，不能用串口到达时间代替；默认不把通用波形发生器、随机引擎和故障脚本处理器一并烧入 FPGA。
- **验收标准**：板外同种子产生同一场景并可重放；实板选装节点的动作时序和资源可验证；未启用故障节点在构建产物中被裁剪。
- **价值与取舍**：允许板外建设完整验证实验室；实时实板注入作为小型可选组件。

## 9. TraceBridge 特色深化

### TB-21：硬件场景重放与故障最小化

- **要解决的问题**：现有 Capture-to-Scenario 已有价值，但完整复现还受输入覆盖、初始状态和采样精度影响。
- **升级内容**：扩展时钟、复位、输入完整性清单；记录多域事件、控制动作与随机种子；自动生成仿真驱动；对可复现失败执行事务裁剪和时间窗口缩小，输出最小失败场景。
- **实现前提**：区分“输入已覆盖”和“内部状态可重建”。从任意中途窗口启动仿真通常还需要复位历史或状态快照；采样间隔内丢失的边沿不能凭空恢复。
- **验收标准**：已知故障在生成场景中稳定重现；缺关键输入、外部存储状态或无法确定时钟时，报告覆盖不足；最小化后的场景仍通过失败判据。
- **价值与取舍**：最适合强化 TraceBridge 的差异化；现有一致性分数不应自动升级为完整因果复现证明。

### TB-22：事务级差分与容差比较

- **要解决的问题**：逐周期严格比较会把合法背压、流水线延迟或相位差也标为错误。
- **升级内容**：保留严格比较，同时提供固定延迟对齐、限定时间容差、忽略区间、掩码字段和事务级匹配；分别比较内容、顺序、响应与延迟。
- **实现前提**：比较规则进入契约或独立版本化配置，报告采用了哪些容差。不能自动扩大容差直到“比较通过”，也不能在未定义顺序规则时打乱事务。
- **验收标准**：合法延迟差异按规则通过；数据错误、丢事务和重复事务仍能检出；每个差异可返回原始样本和规则。
- **价值与取舍**：适合有背压或可变延迟的模块，是现有首差异能力的自然延伸。

### TB-23：带证据的首因候选分析

- **要解决的问题**：静态依赖图中距离最近的上游，不必然就是运行时故障原因。
- **升级内容**：在现有 RootCauseGraph 上加入变化先后、时钟域、复位、协议违规和传播延迟证据；建设可交互证据图、跨会话候选对比和“下一次最值得采什么”的探针建议，按预算主动缩小板端观测集。
- **实现前提**：保留静态结构和动态观测的区别；未采集的中间节点只能作为推测。排序分数要解释来源，不把启发式分数包装成统计概率。
- **验收标准**：对预先注入的若干故障记录候选命中率和排名；每条结论能回到具体波形事件；观测不足时输出下一步采集建议。
- **价值与取舍**：与源码/SFTree/画布联动结合后展示价值高，且可先用确定性规则实现。

### TB-24：自然语言调试助手

- **要解决的问题**：初学者难以把“FIFO 卡住了”等意图转成合适的触发器和采样方案。
- **升级内容**：将自然语言转为候选探针、触发 DSL、资源预算和排查步骤；解释结构化诊断；从会话生成问题报告；支持本地规则模式和可选模型后端。
- **实现前提**：所有建议经契约校验、能力检查和资源估计后才能执行；对构建、下载、控制等操作使用明确的任务动作，结论链接原始证据。模型服务不应成为基础采集的强制依赖。
- **验收标准**：对一组标准意图能生成可验证的配置；不支持功能被拒绝；模型不可用时采集、回放和确定性诊断仍可正常工作。
- **价值与取舍**：适合教学演示，但建议晚于可信数据和分析能力，避免只有对话包装。

## 10. 构建与跨平台系统升级

### TB-25：跨层级语义插桩与探针映射

- **要解决的问题**：顶层或有限内部网插桩不能充分覆盖实际层级、参数化模块和 generate 结构。
- **升级内容**：基于语法/展开结构选择实例内信号，生成影子端口或受控网表探针连接；追踪源信号、实例、综合后网络和采集位偏移；明确优化折叠和常量传播结果。
- **实现前提**：复用现有结构化和映射基础，避免文本正则替换承担 SystemVerilog 语义。列明支持的语言子集、数组和生成块命名规则。
- **验收标准**：嵌套实例、同模块多实例和参数化位宽映射正确；原始 RTL 内容不变；不存在或优化后不可用的探针在下载前失败。
- **价值与取舍**：直接扩展可调试工程规模，是探针选择、首因分析和源映射的共同基础。

### TB-26：调试构建缓存与分级增量更新

- **要解决的问题**：修改触发阈值、探针组或局部插桩时，不应无差别重跑全部工具。
- **升级内容**：区分无需构建的运行时参数、预埋探针切换、需新综合的插桩变化和需重新实现的结构变化；缓存工具输入与中间产物；可用时复用工具链支持的增量布局布线。
- **实现前提**：缓存键包含源、约束、工具版本、目标、插桩核和映射；对 Yosys/nextpnr 当前支持范围做专项验证，不能直接假定具备 Vivado DCP/ECO 的等价能力。
- **验收标准**：运行时阈值变化不调用综合；命中缓存的产物身份一致；约束或工具版本变更必然失效；记录完整/缓存/增量三种耗时。
- **对标与取舍**：借鉴 [Vivado 增量调试工作流](https://docs.amd.com/r/2025.2-English/ug936-vivado-tutorial-programming-debugging/Debugging-Designs-Using-the-Incremental-Compile-Flow?contentId=C2EzGBiRYOWJnPLdxSechw)，先实现可靠缓存，再研究工具链增量能力。

### TB-27：插桩扰动与时序影响评估

- **要解决的问题**：调试逻辑增加扇出、改变布局和时序，可能让原故障消失或制造新故障。
- **升级内容**：比较基线与调试版资源、时钟约束、关键路径和时序结果；标记高扇出探针、组合路径观察及新增采样寄存器延迟；提供轻量探针建议。
- **实现前提**：同目标、同约束、可追溯工具参数的基线；标记报告覆盖范围。时序报告通过不等于逻辑完全等价，也不能保证故障不受观察扰动影响。
- **验收标准**：人为增加高扇出探针能产生可解释差异报告；不满足时序时依配置阻断下载或要求显式接受；映射注明采样流水延迟。
- **价值与取舍**：应与新采集能力同步推进，尤其是在资源紧张的小器件上。

### TB-28：Target Profile 与跨厂商适配

- **要解决的问题**：板卡信息散落在引脚、下载脚本、时钟和协议假设中，扩展目标成本高。
- **升级内容**：Target Profile 统一描述器件、工具链、时钟、复位、调试端口、存储、下载方式、保留引脚和支持能力；逐步覆盖更多 Gowin 板卡，再按需求适配其他厂商。
- **实现前提**：为 BRAM、时钟和厂商专用原语提供适配层；每个目标标记仿真通过、综合通过或实板通过，避免“生成文件成功”被写成完整支持。
- **验收标准**：同一简单 DUT 在两款实际板卡上完成构建、下载和一致采集；不再依赖固定 17/18 引脚或固定 27 MHz 的隐含假设。
- **价值与取舍**：适合平台扩展，但新增厂商意味着持续维护驱动、工具版本和回归硬件。

## 11. 自动化、协作与产品化升级

### TB-29：无界面 CLI / SDK / 任务 API

- **要解决的问题**：GUI 调试过程难以纳入脚本、课程评测和自动化流程。
- **升级内容**：提供校验、构建、下载、连接、布防、等待、回读、重放、比较和归档命令；支持机器可读结果、退出码、超时、取消及进度事件。
- **实现前提**：复用现有 DebugAcquisition/会话/构建服务，不把 GUI 控件当作业务 API；先评估现有 agent 和任务接口能否复用，避免重复暴露同一能力。
- **验收标准**：一条脚本完成样例闭环；失败返回具体阶段和稳定错误码；CLI 与 GUI 的产物结构和判定一致。
- **价值与取舍**：既可对标 Vivado 脚本工作流，也能降低后续 CI 和远程服务成本。

### TB-30：硬件持续集成与板卡池

- **要解决的问题**：软件模型通过不代表真实 UART、时序、引脚和下载流程正确。
- **升级内容**：分层回归包括协议单测、行为模型、生产 RTL 仿真、综合、布局布线及硬件 smoke；增加板卡独占租约、自动烧录、健康检查、失败采集包和历史趋势。
- **实现前提**：区别生产 RTL 与同接口替代模型。当前多时钟 Verilator 示例说明使用小型双域模型，不能将其通过等同于生产采集核完整仿真或多域实板通过。
- **验收标准**：能定位失败属于模型、RTL、工具链还是实板；两项任务不会争用同一块板；失败现场完整保留；离线运行不伪报板测通过。
- **价值与取舍**：适合准备长期维护或多人开发时投入，先用一块固定测试板建立最小流程。

### TB-31：远程调试服务与协作会话

- **要解决的问题**：团队成员不在板卡旁边时，无法复用硬件资源或共同查看故障。
- **升级内容**：板端代理管理设备、串口和烧录；客户端远程提交调试任务、查看状态和获取会话包；支持只读共享、书签、注释和单控制者租约。
- **实现前提**：基于 TB-29 的任务服务，增加身份认证、连接加密、操作审计和权限分离；精确触发留在 FPGA，避免网络延迟进入触发语义。
- **验收标准**：断网可恢复任务状态；只读用户不能控制/烧录；租约过期不会被另一个客户端静默接管正在进行的采集。
- **价值与取舍**：适合实验室和团队板卡池；建议先做局域网代理，再评估跨网络部署需求。

### TB-32：自检、故障诊断与教学向导

- **要解决的问题**：串口占用、错误位流、时钟停摆、引脚错误和触发不满足往往表现为同一个“超时”。
- **升级内容**：启动前诊断目标、工具、引脚、串口、协议、身份和时钟；运行时显示布防/等待触发/已冻结/正在回读等阶段；为 FIFO、复位、UART、状态机提供诊断模板与内置自测设计。
- **实现前提**：统一错误分类和证据字段；只能通过已知证据提示“可能原因”，不能从无响应直接断言硬件损坏。
- **验收标准**：对串口占用、旧位流、能力不符、未触发和断连给出不同诊断；建议可点击进入对应配置；新用户能按向导完成首次采集。
- **价值与取舍**：低到中等成本即可明显提高完成度，建议作为近期优先项。

## 12. 长期创新与生态扩展

### TB-33：长期日志与轻量故障快照

- **要解决的问题**：设备运行数小时后出现异常，开发者通常来不及手工连接和布防。
- **升级内容**：在线时由板外代理做长期日志、周期采集、告警、归档和趋势分析；脱机场景才选装小型循环缓冲、预置触发与少量状态快照，异常后冻结并等待读取。
- **实现前提**：周期采集存在盲区，不能宣称连续记录所有事件；片上缓冲容量与保留条件明确。普通 RAM 不能保证断电保留，非易失存储专项不进入默认核。
- **验收标准**：脱离 IDE 运行时可捕获预置错误，重连后读到正确采集 ID；复位与断电行为符合所选硬件档位；长期计数溢出可识别。
- **价值与取舍**：将长期数据规模和分析压力留在板外；板端只保留小型“最后现场”，不建设默认大型日志系统。

### TB-34：多仿真器与波形格式适配

- **要解决的问题**：只绑定单一仿真器和 VCD，限制既有项目接入与大型数据性能。
- **升级内容**：定义仿真运行器和波形读取接口；在 Verilator 之外按需求支持 Icarus 或商业仿真器；支持 FST 等格式及统一的事件、枚举和源映射元数据。
- **实现前提**：区分仿真中的四态 X/Z 与硬件数字采样值，不把硬件采样数据伪装成能直接识别内部亚稳态或模拟波形；明确时间精度和比较策略。
- **验收标准**：两个仿真器对支持语言子集的参考设计生成可比较结果；格式转换保持值与时间；不支持的语言特性明确报告。
- **价值与取舍**：先做格式和数据接口，再按实际用户需求增加运行器，避免长期维护过多空壳适配。

### TB-35：分析器与设备插件 SDK

- **要解决的问题**：每增加一个协议、板卡或诊断规则都改动核心，难以形成扩展生态。
- **升级内容**：版本化接口覆盖协议解码、断言规则、目标配置、传输适配、导出器和报告生成；规定输入数据、能力、错误及取消语义，提供最小插件示例。
- **实现前提**：优先评估现有 SigFlow 插件 SDK 的复用；需要崩溃隔离的第三方分析器可选择进程外执行，核心数据接口先稳定。
- **验收标准**：不修改 TraceBridge 核心即可加入一个新解码器；插件版本不兼容可定位；崩溃或超时不损坏采集会话。
- **价值与取舍**：适合核心功能成熟后开放，接口过早固定会增加未来兼容成本。

### TB-36：高速串行链路与板级健康监测

- **要解决的问题**：未来复杂板卡可能需要同时分析收发器误码、链路训练、温度和电源状态。
- **升级内容**：主线仅在板外读取目标已有的温度、电源、错误计数和链路状态，关联 TraceBridge 事件并生成报告；PRBS、眼图和专用收发器测试核作为独立硬件研究，不进入默认采集位流。
- **实现前提**：高速收发器、相关管理接口、传感器和驱动均为硬件前提；Tang Nano 9K 不能通过升级 GUI 就获得 IBERT 等价能力。
- **验收标准**：在明确支持的目标上，以可控链路条件产生预期误码/状态变化；标明扫描方法、测量条件和原始结果；没有硬件支持时明确不可用。
- **对标与取舍**：参考 [UG908 的串行 I/O / IBERT 调试范围](https://docs.amd.com/r/en-US/ug908-vivado-programming-debugging)。已有遥测可做丰富的板外仪表盘；新增 SerDes 测试硬件属于专项研究。

## 13. 推荐的实施组合

### 13.1 板端“小而美”组合

默认优先组合：**TB-01、TB-09、TB-27、TB-32**，其中配置、恢复调度、报告和向导主要在宿主实现。按需求再增加 **TB-03** 的必要时钟/复位原语。

- 保留默认单域、32×1024 有限窗口，复用现有触发方式。
- 优先修正配置一致性、协议实现效率和出错后的可恢复性。
- 小批量回读保持流式、有界，不为吞吐堆积大型帧缓存。
- minimal/full 继续明确分档，完整性保证以实际支持为准。
- 以同 DUT 的资源和时序增量作为每个板端改动的门槛。

按任务选装：**TB-02** 少量采样域、**TB-05** 有限实时条件、**TB-07** 门控/时间标记、**TB-17** 少量控制端点。它们不是默认全部开启的功能包，也不是软件平台升级的先决条件。

### 13.2 板外“大而美”主力组合

建议优先组合：**TB-12、TB-13、TB-14、TB-15、TB-16、TB-21、TB-22、TB-23、TB-25、TB-26、TB-29、TB-34**；数据能力成熟后加入 **TB-24**。

- 一个集成工作台联动原始波形、事务、规则、证据图、源码和画布。
- 规则引擎与协议插件可以丰富扩展，新增分析规则无需更换已有位流。
- 仿真重放、故障最小化、容差差分和版本回归承担复杂计算。
- 智能探针规划和缓存减少板端观察宽度与重新构建次数。
- 统一任务 API、数据模型和格式适配，使 GUI、CLI 与后续服务共用同一能力。

这应成为主要产品投入方向。是否需要更多板端探针由具体分析任务决定，不能把“纯软件新增功能”承诺误写成“所有场景都无需增加采样信息”。

### 13.3 如果目标是竞赛展示与差异化

建议组合：**TB-08、TB-12、TB-14、TB-21、TB-22、TB-23**，再按效果补充 **TB-24**。演示刻意采用小型板端采集核，展示主要价值如何由板外软件产生。

可展示的完整故事：

1. 板上捕获一个握手错误。
2. 自动生成包含输入、时钟与复位信息的场景。
3. 在仿真中复现并缩小失败事务。
4. 通过事务差分找到首个偏离事件。
5. 按动态证据给出上游候选，跳转源码和画布，并推荐最小补充探针。
6. 修复后用同一场景回归，导出证据包，同时展示板端资源变化。

该组合延续 TraceBridge 已有特色，展示效果来自可验证的闭环；自然语言解释是增强入口，不应代替复现证据。

### 13.4 如果目标是团队、实验室或多板卡平台

建议组合：**TB-28、TB-29、TB-30、TB-31、TB-35**。

设备服务、租约、远程权限、多人注释、计算调度和会话数据库全部放在板外。先稳定目标配置和无界面任务，再做板卡池与远程协作；FPGA 继续使用对应目标的轻量调试核。

## 14. 分阶段路线与依赖

采用“板端轻量维护 + 板外持续增强”两条可独立推进的路线。共同基础是可信数据，不要求硬件可选能力全部完成后才开始软件开发。

| 路线 / 阶段 | 建议交付 | 验收门槛 |
| --- | --- | --- |
| 共同基础 | TB-01、TB-27、TB-32；协议/契约/schema 一致性与基线 | 默认单域闭环可信；错误有证据；资源和时序可复测 |
| 板端 A：轻量优化 | TB-09；按目标补 TB-03 最小恢复逻辑 | 同 DUT 实测资源可接受；回读正确；未使用功能不占资源 |
| 板外 A：分析工作台 | TB-12、TB-13、TB-14、TB-15 离线规则、TB-16 窗口分析、TB-34 | 在已有采集数据上完成协议、规则和性能分析，无需新增常驻核 |
| 板外 B：重放与定位 | TB-21、TB-22、TB-23、TB-08 探针规划，随后 TB-24 | 已知失败可重放；证据可追溯；补充探针有预算依据 |
| 板外 C：构建与自动化 | TB-25、TB-26 缓存、TB-29 | 插桩只生成必需连接；缓存身份正确；GUI/CLI 产物一致 |
| 板外 D：团队平台 | TB-28、TB-30、TB-31、TB-35 | 目标验证分级；设备隔离；远程权限和协作记录明确 |
| 板端按需分支 | TB-02 少量域、TB-05 小触发逻辑、TB-07 条件采样、TB-17 少量控制端点 | 有具体案例、实测收益与成本；默认构建完全裁剪未启用项 |
| 独立研究分支 | TB-11、TB-19 大型主机、TB-26 工具链增量研究、TB-36 SerDes | 不进入默认路线；具备需求、测试资源和可行性证据后再立项 |

主要依赖关系：

- 多时钟：TB-01 → 按需 TB-02；可靠恢复结合 TB-03；不阻塞单域板外分析。跨域精确关联需要时间标记或同步锚点。
- 协议分析：TB-13 → TB-14 / TB-15；TB-16 可并行建设；它们不依赖板端协议专用核。
- 激励：板外仿真 TB-20 可独立推进；实板节点才依赖 TB-17 / TB-19，按 DUT 现有通道选择。
- 重放定位：TB-12 + TB-21 + TB-22 → TB-23；TB-24 消费这些结构化结果。
- 平台化：TB-28 + TB-29 → TB-30 / TB-31；插件化 TB-35 在核心接口趋稳后实施。

## 15. 架构演进建议

建议保留现有 DebugContract、DebugSession、ITransport、ReplayScenario 等模块职责。板端控制规模，板外按数据、分析、任务和交互拆分，允许建设完整平台。

| 执行位置 / 层 | 建议职责 | 典型对象或模块 |
| --- | --- | --- |
| 板端：默认采集核 | 单域有限采样、现有触发、环形 RAM、必要协议状态 | sf_micro_ila、所选轻量协议核 |
| 板端：选装原语 | 少量域、门控/时间差、有限条件、少量 VIO 端点 | 按任务生成的小型 RTL，构建时裁剪 |
| 板外：配置与构建 | 能力模型、探针规划、插桩、映射、缓存、资源/时序报告 | CapabilitySet、TargetProfile、ProbePlan、BuildCache |
| 板外：设备访问 | 枚举、传输、重试、超时、取消、状态与租约 | DeviceSession、LinkStatistics、BoardAgent |
| 板外：数据底座 | 原始样本、时间语义、窗口/缺口、波形索引与事务存储 | CaptureDataset、WaveIndex、TransactionStream |
| 板外：分析与仿真 | 解码器、规则引擎、性能、差分、重放、最小化、证据图 | RuleEngine、ReplayScenario、AnalysisReport、EvidenceGraph |
| 板外：工作台与平台 | 波形/源码/画布、自然语言入口、CLI、任务 API、会话库和协作 | DebugJob、SessionArchive、分析插件和客户端 |

建议的数据路径：`轻量 FPGA 采集 → 现有链路 → 板外 CaptureDataset → 协议/规则/差分/重放 → 工作台与自动化`。配置与插桩规划反向决定最小必需观测信息，不把分析引擎编译为默认板端硬件。

### 15.1 板端可裁剪档位

以下是未来构建档位建议，区别于目前已存在的 `minimal/full` 协议名，尚不表示已实现：

| 档位 | 包含内容 | 默认行为 |
| --- | --- | --- |
| 基础采集 | 单域、有限 RAM、现有基础触发、所选轻量协议 | 日常默认，板外分析可丰富扩展 |
| 小型增强 | 用户选中的计数/边沿/门控、少量控制或必要身份字段 | 只编译所选原语，分别报增量成本 |
| 少量多域 | 显式选择的额外采集域与必要 CDC、分域回读 | 为该任务生成；单域构建无额外实例 |
| 专项硬件 | 高吞吐、DDR、复杂总线主机、SerDes | 独立位流/目标专项，不捆绑日常默认核 |

档位不能形成“越高级越值得默认开启”的倾向；选择满足当前诊断任务的最小档位即可。板外工作台功能不按 FPGA 核的大小分级。

### 15.2 板外可扩展模块

可独立建设波形与事务索引服务、规则/解码插件、仿真作业池、故障最小化器、会话与版本比较、设备代理、共享注释及可选模型助手。初期可在一个桌面进程中采用模块边界，规模确有需要后再将长任务放到进程外或服务端，不要求一开始部署复杂分布式系统。

特别建议将“原始采集数据”与“VCD 导出”解耦。VCD 可以继续作为兼容输出，但多域时间、缺口、窗口、事务和压缩元数据应有独立的版本化数据模型，否则每次高级功能都需要绕过 VCD 表达限制。

身份信息至少分为：设计/插桩身份、位流身份、运行时配置、采集 ID 和分析规则版本。它们用途不同，不宜只用一个哈希字段包办全部一致性。

## 16. 统一验收原则与量化指标

| 维度 | 应记录的指标或证据 |
| --- | --- |
| 正确性 | 已知输入下样本值、位序、触发点、域内周期和时间差是否正确 |
| 完整性 | 缺块、丢样、覆盖窗口、死区及是否存在重传 |
| 资源 | 同 DUT 下调试增量 LUT/DFF/BRAM，协议档位和各可选模块成本 |
| 板端裁剪 | 纯板外升级是否复用同一位流；未启用原语是否从网表消失；基础档位是否保留不需要的复用树/计数器/缓存 |
| 时序 | 约束、时序结果、采样流水延迟及与基线的变化 |
| 性能 | 有效 payload 吞吐、完整回读时间、构建时间、波形交互响应 |
| 重放 | 输入覆盖、初始状态假设、失败复现次数和最小化后保留的失败条件 |
| 分析 | 协议/断言误报漏报、差分规则、候选排名与证据可追溯性 |
| 可靠性 | 断连、停钟、复位、CRC 错误、错位流、超时和取消后的恢复 |
| 可移植性 | 支持目标、工具版本和验证级别；替代模型与生产 RTL 结果分开 |
| 可用性 | 首次采集成功路径、诊断准确性、配置可发现性和会话可分享性 |
| 板外规模 | 会话数、波形体积、事务索引规模、后台作业时间、内存/磁盘使用及交互延迟，和 FPGA 成本分开记录 |

不预先承诺“零开销”“无限采样”“完全自动定位所有首因”等不可验证目标。每项立项应选择具体设计、采样配置和失败判据，再设定可复测指标。
