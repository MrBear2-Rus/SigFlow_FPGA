# sigflowAgent开发

##  idea 一点看法

关于sigflow的教学版，Agent起到的作用:

1.背景
关于现在的一种大学生学习范式。
由于llm具有庞大的知识储备和智能，现在很多学生的学习，其实都是在蒸馏大模型，很多问题已经不再是直接Google，百度，查文献，翻教材，而是大部分直接接受ai的输出结果(AI已经足够强大，且对于学习情景几乎可信)，配合权威文献，教材或课程使用。
2.问题
那么，将agent原生化，本质上，就是让llm原生化，以方便我们更好的使用llm的知识。我们正好有ds插件，但是问题在于ds插件的使用本身需要人主动去问，不知道项目结构，不能干涉开源工具链，不能了解学生学习基本情况，和手上用一个sigflow，后台网页开一个ds聊天框没有本质区别。甚至，我们的原生ds服务是远远比不上官方的。如何找出创新的，独特的地方，这是sigflowAgent面临的一个问题。
3.需求
我们做Agent，一个直接希望是，站在FPGA经验者的角度，设计更好的自动化教学服务工作流(后续会出文档细化，包括但不限于，记录学生学习历史信息设计定制化系统提示词，根据开源工具报错信息经过llm处理生成教学引导信息，深度结合知名课程如PA和一生一芯官网，设计RAG知识库让Agent据此提供课程链接方便学生跳转学习知识)，换句话说，运用经验者(也就是我们设计者)的知识，来设计一套智能的llm驱动的教学服务系统，使得sigflow用户能够更轻松地从llm上蒸馏到硬件设计知识。

>在此提出一个思考：插件系统是否可以参考dsh，虽然设计初衷可能大相径庭

## 一，核心目标：
为 Sigflow 构建一个原生的、LLM 驱动的 FPGA 教学服务 Agent，把 FPGA 经验者的教学法 固化成 Agent 工作流,让学生在真实 FPGA 工程流中，被持续引导着从 LLM 身上学习硬件设计知识。
>以LangGraph为编排引擎，设计一个双分支的Agent框架。

    工程模式：复用UCAgent的验证工作流和MCP工具，并进行定制化拓展。

    教学模式：构建独立的教学工具链和引导工作流，作为另一个执行分支。

    切换机制：通过运行时配置（RunnableConfig）和条件路由，根据用户选择的模式，动态切换分支、工具和提示词

1. UCAgent简要定位，及其对sigflow的价值：
定位：UCAgent 提供的是一套通用的定制化框架，但它的默认实现和设计重心，完全面向验证领域，是高度特化的。它的默认工作流是一个31 个阶段的细粒度验证流程，每个阶段都配有自动检查器，从需求分析一直到验证总结。它内置的工具也主要是为了服务验证任务，比如编译设计、运行测试、获取仿真结果等。

价值：
工程上，由于其高度特化的验证能力，十分契合我们工程版Agent的一部分业务需求，故原始UCAgent很大一部分可以直接移用在工程版中，利用其验证能力，后续可根据其定制化设计方案拓展其他工程能力。
教学上，其基于硬件设计流程搭建的细粒度工作流，可以为教学工作流设计提供更专业与细致的参考，且其面向工程的模块设计方式可以应用到教学版工作流设计中

2. 第一版目标，教学版：

以 UCAgent 为架构参照，基于 LangChain/LangGraph 生态，先在 Windows 操作系统中，构建 Sigflow 原生的、教学向 Agent 系统。
- 不完全直接套用 UCAgent 代码
- 用它的设计模式和 LangChain 生态能力；
- 用它的 “多阶段工作流 + 检查器” 思想，来设计教学流程（例如：报错诊断 → 知识定位 → 引导生成 → 课程推荐 → 学习记录）。
- 用它的 “工具抽象（UCTool）” 机制，来封装教学能力（例如：RAG 检索工具、学习历史读写工具、课程推荐工具）。
- 用它的 “YAML 配置驱动” 方式，来灵活调整的教学策略，而无需修改核心代码。

1. 操作系统支持。
ucagent原生支持Linux/mac ，但是不支持windows。

硬件验证工具链的缺失：UCAgent依赖 Picker 将Verilog DUT导出为Python包，而这类硬件验证工具链（如cocotb）在Windows原生环境下支持很弱，常出现VPI模块加载失败等兼容性问题。这是移植的最大障碍，因为整个验证流程的基础设施在Windows上不完整。

底层系统调用的差异：Linux和Windows在文件路径、进程模型、信号处理等方面的差异，可能导致一些依赖在运行时出现难以排查的异常。

## 二，模糊需求：

    1.原生集成，而不是外挂聊天框

        Agent 要嵌入 Sigflow IDE，能感知项目结构、代码、约束、仿真/综合日志、工具链报错、用户操作历史。不只是一个需要用户主动提问的 DS 插件，而应主动结合上下文提供教学服务。

    2.教学服务，而不是答案生成器

        当开源工具链报错时，Agent 不是直接甩出修复代码，而是经过 LLM 处理，生成教学引导信息：错误原因、涉及知识点、调试思路、下一步建议。


    3.个性化学习支持

        记录学生学习历史：常见错误、已掌握概念、项目进度、提问偏好。

        根据学习画像动态定制系统提示词，让 Agent 的回答更贴合该学生当前水平。

    4.课程对齐的 RAG 知识库

        深度结合知名课程与资源，如 PA、一生一芯官网、教材、Sigflow 文档。

        构建 RAG 知识库，让 Agent 在引导时能给出课程链接、章节跳转、权威文献引用，方便学生系统学习。

    5.固化 FPGA 经验者的教学知识

        把 FPGA 经验者的调试策略、学习路径、教学经验，设计进 Agent 的工作流、提示词、检查器和推荐逻辑中。

    6.异步、不阻塞 IDE 主流程

        Agent 作为独立进程或后台服务运行，与 wxWidgets/C++ 的 IDE 主线程异步通信。



## 3，模糊计划

### 整体架构：

```
Sigflow IDE（wxWidgets / C++）
        ↕ 本地 IPC / WebSocket / gRPC
Python Agent 服务（LangGraph + asyncio异步或线程池）
        ↕ MCP 协议
MCP Server 层（封装 Vivado / 仿真器 / Tcl / 工具链）
        ↕
Windows 原生 FPGA 工具链 + 开源工具链
```

**教学核心Agent组件：**

- RAG 知识库：PA、一生一芯、教材、Sigflow 文档、FPGA 调试案例。

- 学习历史库：SQLite + 向量库，记录学生轨迹、错误、掌握度。

- LLM 后端：可配置官方 API 或本地模型。

**核心工作流（模糊）：**

    监听 Sigflow 中的事件：编译、综合、仿真、报错、用户操作。
 ->
    采集上下文：项目文件、日志、报错、当前阶段、学生历史。
 ->
    学习画像匹配：判断学生当前水平与已学知识。
 ->
    RAG 检索：从课程知识库中找到相关知识点和链接。
 ->
    LLM 教学引导：生成诊断、解释、引导问题、推荐学习资源。
 ->
    IDE 展示：在教学面板中呈现，支持跳转课程链接、记录反馈。
 ->
    学习历史更新：记录本次交互，调整后续提示词和推荐。


MVP ：

    先做报错教学引导：监听开源工具报错，生成教学解释和调试建议。

    加入课程 RAG 链接推荐：针对错误推荐 PA / 一生一芯相关章节。

    加入学习历史记录：保存学生常见错误和已掌握知识点。

    再扩展主动教学、项目级指导、多课程适配、教学效果评估。
