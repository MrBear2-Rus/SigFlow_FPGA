## 0. 摘要

本规格定义在 SigFlow 现有"任务化 FPGA 流程 + TraceBridge 调试闭环"基础上，引入**双模 AI Agent**：

- **学习模式 Agent（Learn Mode）**：面向学生与初学者，以"引导式教学 + 概念即时解释 + 错误根因讲解"为核心，把 EDA 全流程转化为可理解、可回退、可练习的认知脚手架。
- **工程模式 Agent（Engineering Mode）**：面向工程师与参赛选手，以"意图驱动全量执行 + 闭环自动修复 + 设计空间探索"为核心，对标 ChipOS 类 AI4EDA 产品的"RTL 生成→综合→PnR→验证→调试"一键闭环。

两个 Agent 共享同一套**内核引擎**（意图解析 / 规划 / 执行 / 反思 / 记忆），通过模式切换器在 UI 层呈现不同的交互范式、暴露不同的工具子集、施加不同的安全约束。本文档详述界面调整、工具链增删、数据流、状态机、创新特性与实现路线图。

## 1. 背景与动机

### 1.1 ChipOS 带来的启发

ChipOS 类 AI4EDA 产品展示了"全量执行"范式：用户用自然语言描述需求，AI 自动生成 RTL、驱动综合与布局布线、运行验证、在失败时回溯修复，最终形成闭环。其核心能力可归纳为五点：

1. **意图到代码**：自然语言 → 可综合 RTL。
2. **全流程自动化**：RTL → Yosys 综合 → nextpnr P&R → 打包 → 下载/仿真验证，一条命令贯通。
3. **闭环修复**：验证失败时，AI 读取报告/波形，定位根因，回溯修改 RTL 或约束，重新执行，直到通过或耗尽预算。
4. **多方案对比**：同一需求生成多个实现，横向对比资源、时序、功耗。
5. **自然语言交互**：对话式驱动，降低工具链学习成本。

### 1.2 SigFlow 现状与差距

SigFlow 已具备坚实的执行底座，但在 AI 层几乎空白：

| 维度 | 已具备 | 缺口 |
|---|---|---|
| 综合任务化 | `FpgaSynthesisJob` 状态机完备 | — |
| P&R 任务化 | nextpnr 可运行但由 `MainFrame::RunFpgaRoute()` 直接编排 | **未 Job 化**，无独立状态机/manifest/取消治理 |
| 打包任务化 | Apicula `gowin_pack` 轻量服务 | **未 Job 化** |
| 下载/上板 | openFPGALoader + TraceBridge 调试闭环 | **从未实板验收** |
| 仿真 | Verilator 仿真 VCD 产出 | 仿真未 Job 化，无回归套件 |
| AI 能力 | 无 | **意图解析、RTL 生成、闭环修复、设计空间探索全部空白** |
| 教学 | 示例工程 `rtl/debug/examples/` | 无引导式教学、无概念词典、无错误讲解 |

### 1.3 为什么是"双模"而非单一 Agent

学习者与工程师对同一套 EDA 工具的心智模型完全不同：

- **学习者**需要"为什么"——每个工具在做什么、报错意味着什么、波形如何读、时序违例如何理解。需要高解释性、低破坏性、强引导。
- **工程师**需要"快"——少看解释、多拿结果、能批处理、能探索设计空间、能自动修复。需要高自主性、高吞吐、可复现。

强行用一套交互同时服务两类用户，要么对学习者太晦涩，要么对工程师太啰嗦。双模 Agent 共享内核、分化交互，是兼顾两者的最优解，也能让 SigFlow 同时具备"教学产品"与"工程生产力工具"两种身份。

## 2. 设计哲学

### 2.1 三条原则

1. **内核共享，外壳分化**：意图解析/规划/执行/反思/记忆五件套在两模式下完全相同；UI 布局、工具暴露、安全边界、交互粒度按模式分化。
2. **执行底座先行，AI 搭便车**：所有 AI 动作最终落地为对现有 Job/工具链的调用。AI 不绕过 Job 系统直接执行外部命令，保证可审计、可回退、可复现。
3. **人在回路（Human-in-the-loop）**：工程模式默认自主，但在关键决策点（RTL 大改、约束变更、烧录实板）必须人工确认；学习模式默认人工每步确认，AI 仅建议不代劳。

### 2.2 与 ChipOS 的差异化

SigFlow 不追求"完全替代工程师"，而是：

- **面向开源 FPGA + 教育场景**：Tang Nano 9K 等低成本板卡，而非流片级 ASIC。
- **调试闭环是核心资产**：TraceBridge 的"仿真/硬件双轨 + 首差异定位"是 ChipOS 类产品普遍缺失的能力，SigFlow 把它作为 Agent 反思引擎的关键信号源。
- **可解释优先于全自动**：尤其在学习模式，每一步都要可解释、可回退。

## 4. 目标架构总览

### 4.1 分层架构

```
┌─────────────────────────────────────────────────────────┐
│  交互层 (UI Shell)                                       │
│  ├─ 学习模式外壳 (Learn Shell)                          │
│  └─ 工程模式外壳 (Engineering Shell)                     │
│  共享：模式切换器 / Agent 对话面板 / 执行流水线可视化     │
├─────────────────────────────────────────────────────────┤
│  Agent 内核 (Agent Core)  ← 两模式共享                  │
│  意图解析 → 规划 → 执行 → 反思 → 记忆                   │
├─────────────────────────────────────────────────────────┤
│  执行底座 (Execution Substrate)  ← 现有 + 增强           │
│  Job 系统 (Synth/Pnr/Pack/Flash/Sim/Debug Job)          │
│  工具链 (Yosys/nextpnr/Apicula/openFPGALoader/Verilator) │
│  调试闭环 (sf_micro_ila + TraceBridge)                  │
├─────────────────────────────────────────────────────────┤
│  数据底座 (Data Substrate)                              │
│  .sigflow/ 工程目录 / 契约 / manifest / 会话 / 记忆库    │
└─────────────────────────────────────────────────────────┘
```

### 4.2 模式切换机制

- 顶部模式切换器（Segmented Control）：`学习` | `工程`。
- 切换不销毁工程状态，只切换：可见 DockPanel 集合、Agent 对话面板的系统提示词、工具白名单、安全策略、默认交互粒度。
- 工程可记录"上次模式"，下次打开自动恢复。

## 5. 学习模式 Agent（Learn Mode）

### 5.1 目标用户

- 数字电路课程学生、FPGA 入门爱好者、参赛新手。
- 对 Yosys/nextpnr/约束文件/时序报告缺乏直觉认知。

### 5.2 核心能力

| 能力 | 描述 |
|---|---|
| 引导式全流程教学 | 7 步调试流程的每一步配讲解卡片，AI 解释"这一步在做什么、为什么这么做、产出是什么" |
| 概念即时解释 | 鼠标悬停信号/工具/报告术语，弹出概念卡（定义 + 示意图 + 关联概念） |
| 错误根因讲解 | 报错时不止显示错误，还解释错误成因、修复方向、关联知识 |
| 渐进式示例库 | 从 LED 闪烁 → 分频 → UART → 状态机 → 调试，难度递增 |
| 交互式波形讲解 | AI 逐周期讲解波形含义、标记关键事件、解释毛刺/时序违例 |
| 沙箱与回退 | 所有操作可撤销，工程目录快照化，"我做错了"按钮一键回退 |
| 知识图谱 | 数字电路概念关联可视化，点击节点跳转对应工具/示例 |
| 练习与自测 | 概念 quiz、找 bug 练习、约束填空 |

### 5.3 交互范式

- **高解释性**：每个动作默认带"为什么"展开。
- **强引导**：Agent 主动推进下一步，但需用户确认。
- **低破坏性**：禁止直接烧录实板、禁止修改原 RTL（只允许在副本上操作）。
- **对话式 + 卡片式**：Agent 对话面板在右侧，关键解释以浮动卡片呈现。

## 6. 工程模式 Agent（Engineering Mode）

### 6.1 目标用户

- 熟练工程师、参赛选手、需要批量验证的研究者。
- 目标是"少操作、快出结果、能自动修复、能探索设计空间"。

### 6.2 核心能力

| 能力 | 描述 |
|---|---|
| 意图驱动工程创建 | 自然语言描述需求 → Agent 生成 RTL + testbench + 约束 + 契约 |
| 全量执行闭环 | 一条指令跑通 RTL→综合→P&R→打包→仿真→（上板）→调试，失败自动回溯修复 |
| 闭环修复引擎 | 读取综合/PnR/仿真/调试报告与波形，定位根因，回溯改 RTL/约束，重跑，直到通过或耗尽预算 |
| 设计空间探索 | 参数扫描（流水深度/位宽/复用度），多方案资源/时序/功耗对比 |
| 多方案对比 | 同一需求多实现并行执行，横向对比，择优 |
| 批处理与 CI | 脚本化全流程，回归测试套件，可复现，可夜间运行 |
| 智能调试 | 自然语言描述现象（"LED 闪烁比仿真慢"）→ Agent 跑 TraceBridge → 定位首差异 → 给根因 |
| 约束智能生成 | 从 RTL 推断引脚/时钟约束，生成 CST，冲突检测 |
| 报告摘要 | 综合/PnR 报告自动摘要关键指标 + 风险点高亮 |

### 6.3 交互范式

- **高自主性**：Agent 默认自主执行，关键节点人工确认。
- **高吞吐**：并行多方案、批处理、后台执行。
- **对话式驱动**：顶部命令框 + 右侧 Agent 对话，支持"跑一下""修一下""对比方案 A/B"等口语指令。
- **人在回路门控**：RTL 大改、约束变更、实板烧录三类动作必须人工确认。

## 9. Agent 核心引擎

两模式共享，是本规格的技术核心。

### 9.1 五件套架构

```
用户输入 (自然语言 / UI 动作)
        │
        ▼
┌─ 意图解析 (Intent Parser) ─┐
│  分类: 查询/生成/执行/修复/教学  │
│  抽取: 实体/参数/约束            │
└────────┬───────────────────┘
         ▼
┌─ 规划 (Planner) ──────────┐
│  DAG: Job 依赖图              │
│  预算: 步数/时间/重试上限      │
│  门控: 人工确认点             │
└────────┬───────────────────┘
         ▼
┌─ 执行 (Executor) ─────────┐
│  调度 Job (Synth/Pnr/...)    │
│  收集 manifest/报告/波形      │
│  推送进度事件                 │
└────────┬───────────────────┘
         ▼
┌─ 反思 (Reflector) ────────┐
│  成功: 摘要 + 归档            │
│  失败: 根因定位 + 修复计划     │
│  回溯到 Planner (闭环)        │
└────────┬───────────────────┘
         ▼
┌─ 记忆 (Memory) ───────────┐
│  短期: 当前会话 Job 链         │
│  长期: 工程偏好/修复模式库     │
│  教学: 学习者掌握度画像        │
└────────────────────────────┘
```

### 9.2 意图分类

| 意图 | 学习模式示例 | 工程模式示例 |
|---|---|---|
| 查询 | "什么是时钟域" | "当前资源占用多少" |
| 生成 | "给我一个分频器示例" | "生成一个 UART 回显 RTL" |
| 执行 | "跑一下综合" | "全量执行到仿真通过" |
| 修复 | "这个报错什么意思" | "时序违例帮我修" |
| 教学 | "讲解这段波形" | — |
| 探索 | — | "位宽 8/16/32 对比资源" |

### 9.3 规划与门控

规划器输出 Job DAG，每个节点标注：

- `auto`：自动执行。
- `confirm`：人工确认（RTL 大改、约束变更、实板烧录）。
- `teach`：教学讲解（学习模式默认）。

### 9.4 反思与闭环修复

反思引擎是工程模式的核心创新，流程：

```
执行 Job → 收集产物(报告/波形/日志/门级时序波形)
   │
   ├─ 成功 → 摘要 + 归档 + 结束
   │
   └─ 失败 → 根因分析
            ├─ 综合/PnR 错误 → 改 RTL/约束
            ├─ 功能仿真失败 → 改 RTL/testbench
            ├─ 调试首差异 → 改 RTL/激励
            └─ 门级时序仿真失败 → 改流水/约束/时钟域
            │
            ▼
         修复计划 (Planner) → 重执行 (循环, 直到通过或耗尽预算)
```

**根因信号源优先级**：

1. TraceBridge 首差异（最强信号，硬件实测，区别于 ChipOS 的差异化能力）。
2. 门级时序仿真违例（DTA，实际激励下的建立/保持时间违例，时序相关 bug 的直接证据）。
3. 功能仿真断言失败点。
4. nextpnr PnR 时序报告（fmax/关键路径，粗粒度静态分析）。
5. 综合警告/错误行。
6. 形式验证反例（sby 属性违反，确定性根因）。

### 9.5 记忆系统

| 类型 | 内容 | 学习模式用途 | 工程模式用途 |
|---|---|---|---|
| 短期 | 当前会话 Job 链、最近错误 | 讲解当前步骤上下文 | 闭环修复上下文 |
| 长期-工程 | 工程偏好、常用约束、修复模式库 | — | 加速修复、推荐约束 |
| 长期-学习 | 学习者掌握度、薄弱概念、练习记录 | 个性化教学路径 | — |

记忆持久化到 `.sigflow/agent/memory/`。

## 11. 创新特性

### 11.1 双模共享内核

业界首创：同一 Agent 内核服务教学与工程两种场景，通过模式分化交互。降低维护成本，保证能力一致。

### 11.2 TraceBridge 作为反思信号源

ChipOS 类产品的闭环修复主要依赖仿真与报告；SigFlow 把 TraceBridge 的"仿真/硬件双轨首差异"作为最强根因信号，形成**仿真+硬件双重验证闭环**，这是教育/竞赛场景的独特优势。

### 11.2a 动态时序分析（DTA）三重时序验证

门级时序仿真（nextpnr SDF + iverilog 门级网表）与功能仿真、TraceBridge 硬件实测构成三重时序验证：

- **功能仿真**（Verilator，零延迟）→ 验证逻辑正确性
- **门级时序仿真**（iverilog + SDF，布线后真实延迟）→ 验证激励相关的时序正确性，发现 STA 难以捕捉的时序相关功能 bug
- **硬件实测**（TraceBridge）→ 验证实板真实行为

三者层层递进，比 ChipOS 类产品单纯依赖"功能仿真 + 静态报告"更立体，尤其能定位"逻辑对、静态时序过、但实板仍出错"这类最棘手的时序相关问题。

### 11.3 学习者掌握度画像

学习模式持续记录学习者交互（概念查看、错误类型、练习正确率），构建掌握度画像，动态调整教学路径——已掌握的概念快速跳过，薄弱概念反复强化。

### 11.4 概念即时解释浮层

鼠标悬停任意信号/工具/报告术语，即时弹出概念卡（定义 + 示意图 + 关联概念），把"查文档"成本降到零。

### 11.5 工程快照沙箱

学习模式所有操作在快照上进行，"我做错了"一键回退到任意历史点，消除试错恐惧。

### 11.6 设计空间并行探索

工程模式参数扫描生成多方案 Job 并行执行，资源/时序/功耗横向对比，支持"择优采纳"。

### 11.7 约束智能生成与冲突检测

从 RTL 自动推断引脚/时钟约束，生成 CST，检测与现有约束冲突，减少手工约束错误。

### 11.8 报告风险高亮摘要

综合/PnR 报告由 LLM 摘要，关键指标 + 风险路径高亮，工程师无需逐行读报告。

### 11.9 CI 夜间回归

工程模式生成回归脚本，夜间自动跑全量测试套件 + 等价性检查，第二天早上一份报告。

### 11.10 教学案例自动生成

工程模式的修复记录可一键转化为学习模式的教学案例（"看看这次时序违例是怎么修的"），形成工程实践到教学内容的自动反哺。

- [ ] 自然语言"做一个 UART 回显"→ Agent 生成 RTL + 约束 + testbench。
- [ ] 一条指令全量执行到仿真通过，失败时自动修复（预算内）。
- [ ] 时序违例场景：Agent 读取 PnR 报告 + TraceBridge 首差异，给出根因并修复。
- [ ] 参数扫描生成 ≥3 方案，资源/时序对比可视。
- [ ] CI 脚本可夜间运行并产出报告。

### 13.3 学习模式

- [ ] 7 步流程每步配讲解卡，新手可独立完成一次仿真闭环。
- [ ] 悬停信号/术语弹出概念卡，覆盖 ≥50 个核心概念。
- [ ] 报错时给出根因讲解 + 修复方向。
- [ ] 快照回退可用，误操作可撤销。
- [ ] 学习者画像可记录掌握度并调整路径。

### 13.4 共享

- [ ] 模式切换 <500ms，不丢失工程状态。
- [ ] Agent 对话面板两模式可用，意图分类准确率 ≥85%。
- [ ] 记忆持久化，重启后可恢复。

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| LLM 生成 RTL 不可综合 | 工程模式闭环失败 | 生成后强制 Yosys 综合校验，失败回退到模板 |
| 闭环修复死循环 | 资源耗尽 | 硬预算（步数/时间/重试），耗尽即停并报告 |
| 实板烧录误操作 | 硬件损坏 | 三类门控（RTL大改/约束/烧录）必须人工确认 |
| 概念词典维护成本 | 学习模式内容陈旧 | 词典 JSON 化，社区可贡献；LLM 兜底生成 |
| Job 并行资源竞争 | 系统卡顿 | Job 调度器限并发，CPU/内存配额 |
| 模式切换状态丢失 | 用户体验差 | 切换只改 UI 可见性，工程状态完全保留 |
| 记忆库膨胀 | 性能下降 | 短期记忆会话级清理，长期记忆定期归档压缩 |
| LLM 依赖与离线 | 无法离线使用 | RTL 生成/摘要等强依赖 LLM 的能力降级提示；教学核心不依赖 LLM |
